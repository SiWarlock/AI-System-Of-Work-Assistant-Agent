## Decisions made

- **Cap-then-validate, not validate-then-cap** — the round's most-argued design point on this slice, litigated across three message exchanges with the orchestrator (two reversals, both eventually landing back on the original design). The decisive argument, named late: validate-then-cap would **silently redefine what `entityRefsTruncated` means to its existing consumers** (13.8d, 13.8f-A, and five pre-existing 13.8h tests) — today it means "refs beyond position 200 of the raw model array"; under validate-then-cap it would mean "valid refs beyond position 200 of the valid subset." Same name, same type, different population, and the five pre-existing all-valid-array tests would **still pass**, so the redefinition would land green and silent — exactly the defect class this round spent itself closing, arriving through a change meant to close it. Cap-then-validate keeps `entityRefsTruncated` byte-identical in meaning; only the new field (`entityRefsRejected`) carries new semantics.
- **`entityRefsRejected` is a sibling field, never merged into `entityRefsTruncated`.** The two count strictly disjoint populations by construction (a ref past the cap is truncated and never inspected by the schema at all; a malformed ref within the cap is rejected and never counted as truncated), so a reader can always tell which failure class fired. Merging them would rebuild the exact ambiguity §DEC-CANDGATE exists to remove, one level up.
- **A rejection is surfaced, never silently dropped.** Validate-then-drop-silently would make a poisoned-row attack byte-identical to a benign empty run — precisely the defect §ARM-RESEARCH residual 13.8m records on a sibling channel. `entityRefsRejected` is the count that keeps the two distinguishable.
- **An invalid ref degrades that ref, not the whole plan.** The top-level `planSynthesis` input guard (`workspaceId`/`sourceRefs`) stays untouched — those are genuinely `unusable_input`-worthy (a plan cannot be sourced at all without them), whereas a single malformed model-supplied `entityRef` should drop that ref and keep everything else the run produced.
- **Accepted trade-off, recorded not discovered:** because the cap is positional, a degenerate model output front-loaded with malformed refs can consume the entire cap and starve legitimate refs positioned after it (200 malformed refs followed by 50 valid ones ⇒ the 50 are never resolved). This degrades completeness, never correctness (a suppressed ref writes nothing false), and is judged an acceptable cost of bounding parse-work and read-work to one constant. Documented in-code at the call site and pinned by a dedicated test (`a_front_loaded_malformed_array_can_starve_valid_refs`) so a future reader finds the reasoning rather than rediscovering the behavior.
- **The gate runs once, at the boundary, not per consumer.** `resolveEntity` stays schema-agnostic by design. A deterministic caller (the meeting path's attendee-supplied refs, via `attendee-refs.ts`'s producer and `meeting-rewrite.ts`'s direct `resolveEntity` call) is **not** routed through `collectEntities` and is therefore unaffected by this gate — pinned explicitly (`a_deterministic_caller_supplied_ref_is_unaffected`) rather than left to be inferred from the diff.
- **Bounded reachability claim.** `EntityRefSchema` now has a real, non-test caller (`collectEntities`, invoked from `planSynthesis`) — closing leg 1's "no caller" gap. This does **not** mean `planSynthesis` is wired to production: the pre-existing `no_production_caller` dormancy pin (owned by 13.8d/13.8f, untouched by this slice) still passes. Stating the claim with its boundary rather than letting it be quoted unbounded was an explicit design goal this session, after the round's recurring failure mode of a true-but-scoped claim losing its scope on the next read.

## How to use what was built

Any future caller of `planSynthesis` that wants operator-visible signal on rejected model-supplied entity refs reads `SynthesisOutcome.entityRefsRejected` the same way an existing caller would read `entityRefsTruncated` — both are plain counts (rule 7: never a ref/name/path), 0 meaning nothing of that class occurred this run. Neither field is currently threaded further up into a caller-facing receipt (`IngestRewriteReceipt`/`MeetingRewriteReceipt`) — that threading, if ever wanted, is out of this slice's scope, mirroring the same open thread session 127 already recorded for `entityRefsTruncated`.
