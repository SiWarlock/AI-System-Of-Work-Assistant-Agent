- **13.21 — code-quality review found a real overclaim, fixed in-slice.** The doc comment originally said a future contracts field-add "appears here automatically, still immutable" — true only for primitive fields. `Readonly<T>` is shallow; a future non-primitive field would have its own reassignment blocked but never its contents' mutation. Fixed the comment to state this caveat explicitly and re-verified `tsc --noEmit` clean after the wording-only change. (Notably: this was also an error in the orchestrator's own brief AND their own Step-2.5 approval message, both of which asserted the unqualified "still immutable" claim — the reviewer caught it in the artifact, not in either round of human/agent review that preceded it.)
- **13.8g-C leg C Q1 — pin lives in knowledge's suite (consumer side), not contracts'.** Checked first whether contracts already had a symmetric test (per the brief's explicit instruction) — it does (`packages/contracts/test/models/agent-extraction.test.ts:239-240`, `LIST_VALUED_EXTRACTION_FIELDS declares exactly attendees and decisions`) but that pins the *declared set's own shape*, not any consumer's agreement with it. Not a duplicate.
- **13.8g-C leg C Q2 — no broader scope (cap/nesting behavior) folded into the new pin.** Those are already independently covered: nesting-rejection by the pre-existing `pure_never_throws` test (its mixed-input array already contains a nested `[]` element, withheld as `not_a_string` — this pre-dates leg A and was never a gap), and the three attendee-related caps (contracts' 200-item schema-level reject, knowledge's 2000-entry defensive parse-cost slice, knowledge's 200-ref output cap) confirmed non-conflicting from source, each governing an independent stage.
