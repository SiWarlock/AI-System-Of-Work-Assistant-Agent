## Why this session existed

Close §ARM-RESEARCH arming precondition (8): `planner.ts`'s `collectEntities` awaited one GBrain read per element of the MODEL-supplied `candidate.entityRefs`, uncapped — a degenerate REASON output could drive an unbounded sequential GBrain read loop. ## Decisions made

- **⛔ L88 — `MAX_MODEL_ENTITY_REFS` is a DELIBERATELY INDEPENDENT constant from `meeting-rewrite.ts`'s `MAX_ENTITY_REFS`, same value (200) today but NEVER coupled by reference.** `MAX_ENTITY_REFS` bounds a DETERMINISTIC input the meeting path owns (the correlated attendee/project refs); `MAX_MODEL_ENTITY_REFS` bounds ADVERSARIAL MODEL OUTPUT. Coupling them (even via a shared re-exported constant, circular-import concerns aside) would let a future tuning of one silently retune the other's **threat model** — a change made for "the meeting path can trust 500 attendees now" reasons would simultaneously loosen the bound on what a degenerate model output can do, with no signal that the second thing happened. **⚠ This DIVERGES from 13.8h's own recorded Done-when, which asked for a single shared constant.** The orchestrator overrode that explicitly at Step 2.5 (recorded on task #46) — a later reader who "fixes" this by merging the two constants back into one would be silently reopening the coupling the divergence exists to prevent. Record this here so the divergence isn't mistaken for an oversight.
- **Truncation is surfaced, not silently sliced.** A silent `.slice()` would let a run that fan-out-hijacked entityRefs read as a normal thin run — the same hostile-is-byte-identical-to-benign problem 13.8m-A built the `refusals` channel for on the same receipts. `entityRefsTruncated` is a **count**, not a code list: unlike `GroundedPathRefusal` (which has a real per-item reason domain — `structural_surface` / `unsafe_shape`), truncation has exactly one class ("over budget"), so a count on `SynthesisOutcome` is the correct shape and the correct layer — additive, since neither `ingest-rewrite.ts` nor `meeting-rewrite.ts` reads anything off `SynthesisOutcome` but `.plans` today. Confirmed NOT an Appendix-A model (no `packages/contracts` definition, zero cross-doc references), so no cross-doc row is owed.
- **The hoist was applied proactively, not found by a mutation pass.** 13.8m-A (session 121) discovered its refusals-lost-on-a-late-fault bug only via mutation testing, after shipping the naive version. This session applied that same invariant (hoist the accumulator above the `try`) at design time, and pinned it with a dedicated test (`entity_refs_truncated_count_survives_a_later_fault`) rather than waiting to be told by a failing mutation. First time this round a hoisted-accumulator invariant was pinned proactively rather than retroactively.
- **`regions`/`frontmatter` arrays stay uncapped** — confirmed in scope with the orchestrator before starting. They only assemble data synchronously; `entityRefs` is the one that drives an `await`ed GBrain read per element, which is the actual vector §ARM-RESEARCH item 8 names.

## What generalizes

**A previously-learned invariant is cheapest to apply proactively, not retroactively.** 13.8m-A learned "hoist the accumulator above the try" from a mutation pass finding it missing after the fact (session 121). Applying that same lesson at design time here — before any mutation pressure forced it — turned a fix that cost a full mutation-testing cycle last time into a single test written alongside the initial six.

**RED itself can be vacuous, not just the eventual GREEN.** The usual "assert positive before negative" caution (session 121) is about a passing test hiding a defect; the same failure mode can strike at RED-confirmation time when a test's assertion logic depends on a not-yet-defined constant — an `undefined` loop bound can make a test pass "by accident" before the real implementation exists, which is just as misleading as a negative assertion passing over an empty collection.
