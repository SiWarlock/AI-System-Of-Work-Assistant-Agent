## Decisions made

- **Mirrored 13.8m-A, not 13.8m-B.** `refusals` is REQUIRED, not optional. 13.8m-B made the analogous worker-seam field optional to keep 13 pre-existing containment fakes valid — a recorded compromise ("a future adapter could omit it and the sink would silently never fire"), not a design intent. There are no fakes to migrate on this receipt (confirmed by repo-wide grep: zero consumers of `MeetingRewriteReceipt` outside this module and its own test, and no test in the suite constructs a full receipt literal), so copying B's optionality would have propagated a recorded bound onto a second path for no reason (contracts L105/L103).
- **The brief's premise was wrong, and the real discard point is different from what it named.** The brief pointed at this module's own `admitInto(resolution.path, …)` call (line ~190 pre-slice) as where a poisoned resolved-candidate path would be caught. It isn't, and can't be: `resolveEntity` (entity-resolver.ts) already runs `admitGroundedPath` internally on a resolved candidate's path (13.8k) and returns `withheld(reason)` on failure — so `resolution.kind` is never `"resolved"` for a poisoned candidate in the first place. The `admitInto` call the brief named is dead for this purpose; the real, previously-undiscovered discard point is `resolution.reason` on the `withheld` branch, which nothing in this file read before this session. Wired the new branch there instead, plus the seed check (`admitGroundedPath(input.meetingNotePath)`, which aborted the whole run with zero signal).
- **Deliberately did NOT thread a refusals accumulator through `admitInto`'s three call sites** (meeting-note re-registration, resolved-path re-admission, stub-path admission). All three are provably unreachable-to-fail: the first two re-validate a value `admitGroundedPath` (via `resolveEntity`, for the second) already admitted — a pure function, same input always gives the same output, so re-checking it can never newly fail; the third (a minted stub path) is namespaced-safe by construction (13.8j), and security-reviewer independently verified this against `entitySlug`'s actual implementation (strips to `[\p{L}\p{N}-]`, capped at 120 chars — cannot produce `/`, `..`, or a structural-surface name). Adding a refusals parameter there anyway would be speculative, permanently-untested code — exactly the "a guard never observed to fail is indistinguishable from one that cannot fail" shape (contracts L75). Simplicity over defensive-looking coverage that can't be exercised.
- **The withheld branch narrows to exactly the two `GroundedPathRefusal` members** (`structural_surface`, `unsafe_shape`) via a literal-equality check (`reason === "structural_surface" || reason === "unsafe_shape"`), which TypeScript narrows correctly with no cast. The other 5 `WithheldReason` members are read but deliberately not pushed — see the Finding below; this was not an oversight, it's the field's stated scope (it mirrors `GroundedPathRefusal`, not the broader union).
- **Mutation-verified the hoist**, per the brief's explicit instruction: temporarily changed the `catch` block to return a hardcoded `refusals: []` instead of calling `empty()`. Exactly one test went RED (`fault_after_admission_still_reports_refusals`); all 24 others stayed green. Reverted; re-confirmed 25/25 green and clean typecheck.
- **The required-field pin (`refusals_is_required_on_the_receipt`) is proven via `pnpm typecheck`, not `vitest run`.** A `@ts-expect-error` directive on a receipt literal omitting `refusals` is RED before the field exists (`TS2578: Unused '@ts-expect-error' directive` — the directive has nothing to suppress) and GREEN after (the directive is now used, suppressing a real `TS2741`). `vitest run` never surfaces this either way since it doesn't type-check test files — this is the one test in the slice that Step 3/5 confirmed via `pnpm typecheck`, not the test runner.

## The finding this session surfaces (own words, as requested)

**This slice's own new branch is now the ONLY place in the codebase that reads a `WithheldReason`, and it deliberately drops 5 of 7 values — the same shape it was built to close for the other 2.**

Concretely, verified by repo-wide grep before writing this: `WithheldReason`/`EntityResolution` (the specific types declared in `entity-resolver.ts`) are referenced in exactly three non-test files — `entity-resolver.ts` itself (produces the value), this session's `meeting-rewrite.ts` (now reads `.reason`, but narrows to only 2 of the 7 possible values), and nowhere else. `planner.ts`'s `collectEntities` — the SOURCE path's consumer of `resolveEntity`, untouched by this or the prior 13.19 session — calls `resolveEntity` and passes the result straight into `stubNotePathFor(res, …)`; it never reads `res.reason` at all, on any of the 7 possible reasons, on either path.

So today: `ambiguous`, `lossy_match`, `gbrain_unavailable`, `malformed_entity`, and `ws_scope_mismatch` are each computed by `resolveEntity` and then observed by nothing, on both the source path and the meeting path.

**Severity, precisely stated — isolation holds, detection is lost, and the stronger phrasing would be false.** `ws_scope_mismatch` fires at `entity-resolver.ts`'s "1. WS-8 defense-in-depth" check (`deps.gbrain.workspaceId !== workspaceId`) — a safety-rule-4 guard. When it fires, the read genuinely never happens: the function returns `withheld("ws_scope_mismatch")` before any query is issued, so nothing crosses the workspace boundary. **The isolation guarantee itself is intact.** What is lost is that the ATTEMPT is unobservable — a cross-workspace query attempt (whether from a real misconfiguration or a scoping bug) produces exactly the same silence as an ordinary no-match. Calling this a "rule-4 breach" would overstate it (no data ever crossed); calling it "nothing to see here" would understate it (a genuine misconfiguration would be invisible until something downstream noticed the absence some other way). The accurate frame is: **an observability gap on a safety rule**, matching the contracts L106 shape (a correctly-typed signal reaching no consumer is indistinguishable from the failure it was built to distinguish) — a 4th instance, and the first on an isolation rule rather than an audit path. Tracked as task #13, not fixed here.

The lesson I'm taking from this, stated plainly: a design review's value isn't only "is this test correct" — it's the adjacent questions a fresh reader asks that the person who just wrote the code won't think to ask themselves, because they're already inside the frame the code established.
