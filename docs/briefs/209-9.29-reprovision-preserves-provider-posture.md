## ⛔ Why this blocks 9.22

9.22 (option C) derives `zeroEgressOnly` partly **from `providerMatrix`**. While a re-provision can
silently wipe that input, 9.22's claim is computed from volatile state — an empty matrix satisfies
option C's axis 1 *vacuously*, so the surface would report zero-egress **for a reason the owner never
chose, on the exact screen they check to confirm a revoke landed.** The claim would not be *false* (an
empty matrix genuinely routes nowhere) — which is precisely why it is dangerous rather than obvious.
**Lead ruling: 9.29 lands BEFORE or WITH 9.22.**

## ⚠ FIRST DELIVERABLE IS A REACHABILITY TRACE, NOT A FIX

Before writing the carry-forward, establish **by reading the code** and report at Step 2.5:

> **Does any production path mutate `providerMatrix` or `defaultVisibility` AFTER provisioning?**
> Cite `file:line` for each writer found, or state positively that none exists.

**This determines the honest shape of the slice, and the answer may be "no code change":**
- **If a post-provision writer exists** ⇒ the reset destroys real owner-set state ⇒ carry forward (the
  9.23 shape).
- **If NO writer exists** ⇒ these fields are provisioning-owned today, the reset is currently a no-op,
  and carrying forward is speculative. The honest deliverable is then a **documented invariant plus a
  pin** that fails the moment a post-provision writer appears — not a carry-forward for a state that
  cannot yet differ. **Say so and stop; do not write code to be safe.**

Do not skip this. 9.24 established the same discipline and the trace changed that slice's scope too.

## ⚠ This is NOT simply "do what 9.23 did" — the safety direction is INVERTED

9.23 carried a **revoked** (restrictive) state forward. This slice would carry forward a possibly
**permissive** one:
- `rawCloudEgressEnabled: true` would now survive a re-provision that previously re-closed it.
- A **widened** `defaultVisibility` would survive a re-provision that previously re-isolated it (WS-8).

That is why 9.29 was deliberately held out of 9.23 rather than bundled. **You must argue each field on
its own merits and say so at Step 2.5** — "9.23 did it this way" is not sufficient justification for
either field.

## Things to flag at Step 2.5

1. **The trace result** (above) — the load-bearing one. Report before anything else.
2. **`rawCloudEgressEnabled` — preserve or reset?** It is inside `providerMatrix`, so a whole-object
   carry preserves it. My default vote: **preserve, if and only if the trace finds a real writer** —
   otherwise it is a speculative carry of a field nothing sets. If you find it is *never* set true
   anywhere, say so; that materially shrinks this slice.
3. **`defaultVisibility` — same question, WS-8 flavored.** Resetting to `"isolated"` is the restrictive
   direction; preserving a widened value is not obviously right. My default vote: **treat it separately
   from `providerMatrix`** and let the trace decide each. Do not bundle them into one "carry the rest"
   change.
4. **Whole-object carry or per-field?** 9.23 used whole-object precisely so a named-field copy cannot
   silently drop a field this build does not name. My default vote: **whole-object, same reasoning** —
   but the `.strict()` re-parse must cover it, so confirm the parse still runs on the reassembled
   aggregate.
