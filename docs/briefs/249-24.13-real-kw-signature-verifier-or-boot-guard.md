# /tdd brief — real_kw_signature_verifier_or_fail_fast_boot_guard

## Feature
Replace `defaultVerifyKwSig`'s non-cryptographic placeholder (checks only that a string is non-empty) with a real HMAC verifier mirroring the already-shipped `provenance-stamp.ts` pattern — OR, if the real verifier isn't scoped for this slice, add a load-time/CI boot guard that refuses to boot if `reconcileVault` is ever wired into a composition root while `defaultVerifyKwSig` is still the active verifier.

## RED test outline (Step 2)
**If Path A:**
1. **`verify_kw_sig_rejects_empty_signature`** — Asserts: empty/non-empty-but-invalid signature fails verification. Why: baseline the placeholder already accidentally got right by luck, now for the right reason.
2. **`verify_kw_sig_accepts_valid_hmac`** — Asserts: a correctly-signed `(path, contentSha)` pair verifies. Why: the real positive case.
3. **`verify_kw_sig_rejects_sha_mismatch_even_with_valid_sig_format`** — Asserts: a well-formed but wrong signature for the given content is rejected. Why: this is the exact bypass the placeholder allowed — "any non-empty string" — now closed.
4. **`verify_kw_sig_rejects_tampered_content_sha`** — Asserts: changing `contentSha` after signing invalidates the signature. Why: the module's own header claim — "a content-sha match AND a verifying sig, a sha match alone is never enough."

**If Path B:**
1. **`boot_guard_fires_when_reconcile_vault_wired_with_placeholder_verifier`** — Asserts: composing `reconcileVault` into a boot path while `defaultVerifyKwSig` is the active verifier throws/refuses to boot.
2. **`boot_guard_silent_when_reconcile_vault_unreachable`** — Asserts: current state (zero production callers) does not trip the guard — confirms no false-positive.
3. **`boot_guard_silent_when_real_verifier_active`** — Asserts: wiring `reconcileVault` with a real verifier does not trip the guard.
