## ⛔ Owner ruling — read before Step 0

This is **Option C of four**, chosen by the owner: *re-establish immutability at knowledge's consumption sites.*

⛔ **Do NOT add `readonly` to contracts' `EntityRef`. Do NOT open the ~30-model contracts arc.** Contracts' non-readonly convention for Appendix-A seam models is deliberate and stays untouched — it is **0 of ~30**, and `entity-ref.ts:25-27` documents that it matches its neighbours on purpose.

## ⭐ What was actually lost — read this, because the code looks like it already holds

Knowledge's consumption sites already say `readonly entityRefs?: readonly EntityRef[]` — `planner.ts:83`, `planner.ts:348`, `attendee-refs.ts:54`, `attendee-refs.ts:56`, `meeting-rewrite.ts:70`, `meeting-rewrite.ts:80`.

⛔ **`readonly T[]` prevents replacing an ELEMENT. It does nothing about `arr[0].name = "x"`.**

13.19 deleted knowledge's own `EntityRef` — which carried `readonly name` / `readonly kind` — and re-exported contracts', whose fields are mutable. ⇒ **the element-level guarantee vanished while every array-level `readonly` stayed in place and kept the code looking protected.** That is why it passed review, and it's the thing to keep in mind if any of this starts feeling redundant.

## ⛔ The objection this slice must defeat, not merely survive

*"Isn't this re-adding the duplicate that leg 2 deleted?"* — **No, and the distinction is the whole design:**

- Leg 2 deleted a **separately DECLARED** interface with **its own field list**, which could **drift** from contracts' version. Two structurally-identical declarations, independently maintained. That was the defect.
- A **DERIVED** narrowing over the imported contracts type **cannot drift**, because it is *computed* from the single source of truth. Add a field in contracts and it appears here automatically, still immutable.

⇒ **Declared duplication and derived narrowing are different things, and only the first was ever the problem.** Say this in the commit message — the next reader will have leg 2 fresh in mind and will otherwise read this as a regression.

## Things to flag at Step 2.5

1. ⭐ **How is the derived form expressed and named?** (a) re-export under the *same* name `EntityRef`, aliasing the contracts import internally — every existing consumer gets it with **zero call-site churn**. (b) a distinctly-named immutable alias that consumers must opt into. **My default vote: (a), fairly strongly.** It's what makes the guarantee **inherited rather than remembered**, which is precisely the cost the owner flagged when choosing C. (b) reintroduces exactly the "someone has to remember" problem the ruling accepted as C's weakness — **when we can cheaply avoid it, we should.** ⚠ Flag if same-name re-export creates a confusing shadow at the import site, or if `Readonly<>` over a type with a branded/nested member behaves unexpectedly.
2. **Does `packages/evals` receiving the narrowed type need coordinating?** It gets it transitively via the barrel. **My default vote: no — verify by compiling, don't coordinate.** It only reads `ref.name`, so a narrowing is invisible to it, and a *tightening* that another area can't violate isn't a boundary crossing. ⛔ **But if its suite goes red, STOP** — that's a finding and it means the narrowing is broader than intended, not something to patch around.
3. **Is there a cheap pin for "a FUTURE consumer inherits this"?** The owner asked this explicitly. **My reading, to confirm or refute:** a choke-point pin (test 1) covers everyone importing through knowledge's intended path — **which is inheritance, for that path.** What it cannot cover is someone importing `EntityRef` **directly from `@sow/contracts`** inside knowledge. ⛔ **Do NOT write a scanner over import statements for that** — it's a negative claim over an unbounded space, i.e. a detector not a gate, and 9.39 deleted one earlier today for exactly this reason. **Record the residual in-code at the choke point instead.** Tell me if you see a genuinely structural way to close it; don't invent a scanner to look thorough.

## Lessons-logged candidates anticipated

- ⭐ **`readonly T[]` and `readonly` fields are different guarantees, and the first hides the absence of the second.** Six consumption sites all read as protected while the element-level guarantee was gone. That's the strongest candidate here — **an array-level modifier that makes a missing element-level one invisible.** Check whether L103's family already covers it before banking.
- **Declared duplication vs derived narrowing** — a type that *looks* like the duplicate a prior slice deleted but structurally cannot drift. Worth a line if it isn't already implied by existing entries.
- **Crossing a convention boundary between two packages is a distinct defect from violating one.** 13.19 was reviewed by two reviewers and passed, because within each package's own frame nothing was wrong.
