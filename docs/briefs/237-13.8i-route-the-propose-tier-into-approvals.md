## ⚠ SAFETY POSTURE — read before scoping
This slice touches the **§9.8 Approvals gate**, the mechanism that stops human-relevant semantic edits

change here would let a `requiresApproval !== false` plan reach `commit`, that is a stop-and-escalate,
not a bug to fix in-slice.

## Acceptance criteria (what "done" means)
**(a) — PROPOSE → Approvals. Its OWN commit.**
- [ ] Each withheld plan mints **exactly one** PENDING §9.8 Approval carrying `subjectKind:
      "semantic_mutation"` + a `planRef` to that plan, through the **existing** sink path — not a
      second minting site.
- [ ] **Idempotent on re-drive:** re-running the same source-ingestion run does **not** mint duplicate
      Approvals for the same plan. Derive the key from stable inputs (the plan's own `planId` is the
      obvious candidate — confirm it is stable across a re-drive before relying on it; **Step-2.5 Q2**).
- [ ] **The AUTO tier still commits, unchanged and pinned as such.** A `requiresApproval === false`
      plan takes the identical path it takes today — assert this rather than assume it (L79: adding a
      branch silently re-points existing fixtures).
- [ ] ⛔ **A `requiresApproval !== false` plan still NEVER reaches `deps.commit.commit`** — pinned
      directly, with the strict `!== false` intact. This is the invariant the slice exists to preserve
      while changing what happens *instead*.
- [ ] A mint failure is **surfaced, never silent, and never a downgrade to auto-commit** — the plan
      stays withheld and the health surface reports it. ⚠ Decide fail-open vs fail-closed explicitly
      for the mint fault and state it in-code: the safe direction is *the plan is not committed and the
      operator is told*, never *commit it because the queue is broken*.
- [ ] The existing `conflict_review` health surface is **reconciled, not duplicated** — once plans are
      genuinely queued, a bare count may be redundant or may want re-wording. Decide, don't leave both
      asserting overlapping things (L94).

**(b) — restore `planIds`. May be its own commit.**
- [ ] The worker seam carries `planIds` from `IngestRewriteReceipt` through to where a batch-undo could
      consume it; the ordered list survives intact (order is the undo semantics, not decoration).
- [ ] ⛔ **Do not invent an undo executor here.** The task's Done-when is that the receipt *carries*
      `planIds` through to a single batch-undo unit — if no consumer exists yet, that is an **L106**
      situation: name the consumer as a tracked task in this round, or record the absence explicitly
      with the scoped claim. **Step-2.5 Q3.**

- [ ] `/preflight` clean — report as **"typecheck + tests clean; no lint coverage exists."**

## Things to flag at Step 2.5
1. **Call `copilotProposeKnowledgeSink`'s minting directly, or extract its core into a shared helper?**
   Default vote: **extract only if calling directly forces a dependency inversion** — otherwise reuse
   in place. ⚠ The task says *"reuse it, never a second propose sink"*; a shared extraction is still
   one sink, a copy is not. If extraction is needed, the extracted core must be the **only** minting
   site afterward (contracts L39).
2. **Idempotency key.** Default vote: the plan's own `planId`, **if** it is stable across a re-drive —

   re-drive reproduces the same ids or fresh ones). If they are fresh per run, the key must come from
   something content-derived, and that changes the design.
3. **`planIds` with no consumer — what is the honest disposition?** Default vote: thread it, and if no
   batch-undo executor exists, **name the consumer as a tracked task this round** and write the scoped
   claim (L106). ⛔ Do not let (b) ship as "batch-undo restored" when nothing can undo.
4. **Does the existing `conflict_review` health item stay?** Default vote: keep a surface but re-word it
   to reflect *queued for approval* rather than *withheld and dropped* — the operator-facing meaning
