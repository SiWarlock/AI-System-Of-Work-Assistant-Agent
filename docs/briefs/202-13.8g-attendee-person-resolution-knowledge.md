## Acceptance criteria (what "done" means)
- [ ] An exported pure function maps raw attendee strings → `readonly EntityRef[]` with `kind:"person"`, suitable for `MeetingRewriteInput.entityRefs` without further massaging.
- [ ] **A display name is only ever taken from evidence in the string, never synthesized.** `"Jane Doe <jane@acme.com>"` ⇒ name `Jane Doe`. A bare email with no display part does **not** get a name invented from its local-part (`jane.doe@` ⇒ NOT "Jane Doe") — see Step-2.5 Q1 for what it does instead.
- [ ] **Non-person attendees never become person refs** — conference rooms / resources / distribution lists / group aliases are excluded deterministically, not by model judgement.
- [ ] Duplicates collapse (same person listed twice, or once by name and once by email, where the string evidence makes them provably the same).
- [ ] **No-inference (REQ-F-017):** an unparseable / evidence-free string is DROPPED or withheld with a reason — never a `TBD`-named person, never a guessed identity.
- [ ] **WS-8:** the normalizer never attaches or infers a workspace binding; it emits refs only, and an attendee can never smuggle a cross-workspace bind.
- [ ] PURE + never-throws: malformed input (null, non-string elements, absurd length) yields a fail-safe empty/partial result, no exception escapes.
- [ ] Bounded: the attendee list is capped, sharing the cap constant with the existing deterministic caps rather than introducing a second one.
- [ ] Dormant: no `apps/` or `packages/workflows/` importer, pinned via the shared `test/support/dormancy-pin.ts` predicate (reuse it — do not write a third variant).
- [ ] `/preflight` clean.

## RED test outline (Step 2)

## Things to flag at Step 2.5
1. **Bare-email attendee with no display name — drop, or emit a ref keyed on the email?** (a) drop entirely; (b) emit `{name: <the full email>, kind:"person"}` and let the resolver's alias matching resolve-or-withhold; (c) invent a name from the local-part. My default vote: **(b)** — the email IS evidence of a person, just not of a *name*; passing it verbatim lets the resolver match a real person note by alias and WITHHOLD when there's no match, which is the no-inference-correct outcome. (c) is forbidden. Push back if (b) risks minting an email-titled stub note — if it does, prefer (a) and say so.
2. **How is a non-person attendee identified deterministically?** Options: a resource/room prefix convention, an explicit exclusion list, a structural heuristic (no display name AND a group-shaped local-part like `team@`/`all@`/`room-`). My default vote: **structural + a small explicit exclusion set, fail-safe toward EXCLUSION** — a missed person is recoverable; a conference-room person note is vault corruption a human has to clean up. Name whatever rule you pick in the module header.
3. **Where does the cap live?** My default vote: **reuse the existing `MAX_ENTITY_REFS` constant** rather than a second attendee-specific cap — two caps that can drift is the same defect class as two predicates. If the semantics genuinely differ, say why.
4. **Does 13.8g-A own dedupe, or does the resolver?** My default vote: **13.8g-A dedupes the obvious string-evidence duplicates; the resolver remains authoritative for identity** (two different strings resolving to the same note is its call, not yours) — so dedupe conservatively and never merge on a guess.
5. **Module name + whether this is one function or a small module.** My default vote: one exported normalizer plus its types, in `synthesis/attendee-refs.ts`. Cosmetic — take it or rename.
