# /tdd brief — reprovision_preserves_revoked_ack (9.23)

## Feature
Stop workspace re-provisioning from silently restoring a revoked employer raw-cloud-egress acknowledgment. Seed the egress allowlist only on a genuine fresh create; on a same-type idempotent overwrite, carry the stored `egressPolicy` forward verbatim.

## Use case + traceability
- **Task ID:** 9.23 (`IMPLEMENTATION_PLAN.md` task 9.23) · ⚠ **rule-5 FAIL-OPEN closure** · ⛔ **owner-ordered to land BEFORE 9.21**
- **Architecture sections it implements:** `ARCHITECTURE.md §5` (rule-5 egress veto), `§16` (audit)
- **Related context:**
  - **The defect** (verified in code by the orchestrator AND independently by the lead): `apps/worker/src/composition/provisionWorkspace.ts` seeds the egress allowlist at **~L161** (`workspace = seedCloudCopilotAllowlist(workspace, at)`) — **before** the existence check. For `employer_work` that seed sets `employerRawEgressAcknowledged: true` + a fresh `acknowledgedAt` (`:68-76`). The existence check then deliberately falls through on a same-type match (**~L169**, its own comment: "exists, SAME type → an idempotent overwrite (fall through)"), and **~L188** `workspaceConfig.upsert(workspace)` writes the freshly-seeded policy over the stored one. **The stored `egressPolicy` is never re-read or preserved.**
  - **Consequence:** the 9.10-B owner revoke (`225c10ca`) is **not durable**. After a revoke, any later `onboarding.createWorkspace` for that same workspace silently restores ack=true — **no audit row** (the revoke command audits; provisioning does not audit a restoration) and **no owner confirm**. The revoke's guarantee currently holds only as long as nobody re-provisions.
  - **Why it must land before 9.21:** 9.21 (idempotent scaffold repair/resume) IS a re-provision path — it is exactly what turns this from hard-to-reach into routinely reachable. Owner-ordered sequencing; encoded as a `blockedBy` on the task list.
  - **Discovery path:** surfaced by desktop while building the 9.10-C egress surface (its Step-9 Finding 1), i.e. found by building the surface that *displays* the posture — worth remembering as an argument for building the observability surface early.

## ⚠ This is not a new rule — it is worker Lesson 30, under-applied
Worker **L30** (`apps/worker/LESSONS.md#30`) already states the governing rule: *"a workspace-bound operational record's binding anchor (`workspaceId`, **or a field deriving the isolation class**) is immutable-by-default — guard the creation/register path with **get-before-upsert** (same-binding idempotent, changed-binding ⇒ typed `*_immutable`, get-fault fails closed); the guard is composition-layer so every writer must preserve the binding."*

L30's own wording covers this field. It names *"a field like a workspace `type` that DERIVES the isolation classification / **egress-veto applicability**"* as an anchor — and `employerRawEgressAcknowledged` **is** the egress-veto applicability signal. The implementation applied L30's get-before-upsert to `type` and never extended it to `egressPolicy`, even though the same `upsert` call overwrites both. So frame the fix as completing L30's application, not as inventing a guard: the `get` already happens at ~L169 for the type check — its result simply isn't used to preserve egress state.

## Acceptance criteria (what "done" means)
- [ ] **`re_provision_preserves_a_revoked_ack`** — a revoke followed by a same-type re-provision of the same workspace leaves `employerRawEgressAcknowledged: false` and does NOT restore `acknowledgedAt`.
- [ ] A genuine **fresh create** (`not_found`) still seeds exactly as before — employer `[claude]` + ack=true + `acknowledgedAt`; personal `[claude]` + ack unchanged (byte-equivalent to today for the create path, so the 9.10 flip is not regressed).
- [ ] On a same-type overwrite, the stored `egressPolicy` is carried forward **verbatim** — not merged, not re-seeded, not partially defaulted. A re-provision changes `name`/`vaultRoot`; it never changes egress posture.
- [ ] The **type-immutability guard is unchanged** — a different-type re-provision still rejects with the typed `workspace_type_immutable`, and a genuine store fault still fails closed (never falls through to create on unknown prior state).
- [ ] The fix holds for **all** workspace types, not just `employer_work` — a personal workspace's posture is equally not-provisioning's-to-rewrite.
- [ ] A store-fault on the existence read still fails closed and performs **no** upsert.
- [ ] `/preflight` clean + repo-wide `turbo typecheck`.

## RED test outline (Step 2)
1. **`re_provision_preserves_a_revoked_ack`** — Asserts: seed → revoke (ack=false, `acknowledgedAt` cleared) → same-type re-provision ⇒ ack still `false`, `acknowledgedAt` still absent. Why: the whole point; rule-5 durability of an owner decision.
2. **`fresh_create_still_seeds`** — Asserts: `not_found` ⇒ employer gets `[claude]` + ack=true + `acknowledgedAt`; personal gets `[claude]`. Why: non-vacuity — a fix that disabled seeding would pass test 1 while breaking the 9.10 flip.
3. **`same_type_overwrite_carries_policy_verbatim`** — Asserts: a stored policy with a non-default shape (e.g. extra/absent processors) survives a re-provision unchanged, field for field. Why: verbatim, not merged — a partial default is the same class of silent rewrite.
4. **`same_type_overwrite_still_updates_name_and_vaultroot`** — Asserts: the legitimate idempotent-overwrite behavior still works. Why: the fix must not turn a re-provision into a no-op.
5. **`different_type_still_rejected`** — Asserts: typed `workspace_type_immutable`, no upsert. Why: L30's existing guarantee is untouched.
6. **`store_fault_fails_closed_no_upsert`** — Asserts: a non-`not_found` get fault ⇒ typed `store_fault`, zero upsert calls. Why: never fall through to create on unknown prior state.
7. **`personal_posture_also_preserved`** — Asserts: a personal workspace whose policy was modified post-provision is not re-seeded on re-provision. Why: the rule is about provisioning's authority, not about employer specifically.

## Things to flag at Step 2.5
1. **Where does the seed move to?** (a) call `seedCloudCopilotAllowlist` only inside the `not_found` branch; (b) keep the call where it is but overwrite the result with `existing.value.egressPolicy` on the same-type branch; (c) pass the existing policy into the seed helper and let it decide. My default vote: **(a)** — it makes the invariant structural ("provisioning seeds only what it creates") rather than corrective, and there is then no window in which a seeded-but-not-yet-overwritten policy exists in the local variable. (b) works but leaves the footgun in place for the next editor; (c) widens a `packages/` helper's responsibility for no gain.
2. **Verbatim-carry vs field-by-field copy.** My default vote: **assign the whole stored `egressPolicy` object** rather than copying named fields — a field-by-field copy silently drops any field added to `EgressPolicy` later, which is exactly how this class of bug recurs. If a typed spread is needed for `exactOptionalPropertyTypes`, keep it exhaustive and add a comment saying why.
3. **Should a re-provision that WOULD have changed egress posture emit an audit row or a health item?** My default vote: **no, out of scope** — it now changes nothing, so there is nothing to audit. Flag it if you think a "provisioning declined to alter egress posture" signal has operator value; I'd rather not add a log sink on this path (rule 7 surface) without a reason.
4. **Is `provisionWorkspace` genuinely the only writer of workspace config?** Please actually check (`grep` for `workspaceConfig.upsert`) and report at Step 7.5. My default assumption is yes, but L30 explicitly warns that a direct `repo.upsert` bypasses a composition-layer guard — if a second writer exists, that's a Step-9 Finding, not something to fix inside this slice.
5. **Does the same under-application exist for other seeded fields?** If `seedCloudCopilotAllowlist` (or any sibling seeder) touches other durable owner-set state that a re-provision would clobber, name it at Step 2.5 — I'd rather scope it in deliberately now than discover a second instance later.
