# /tdd brief — surface_the_partial_scaffold_repair_state (9.21-B, desktop consumer leg)

## Feature

Consume worker's typed `partial_scaffold` outcome so a partially-provisioned workspace surfaces an honest, actionable **repair/resume state** instead of the generic create-failed message — **without** re-opening the redaction hole that the current blanket fold exists to close. ## ⛔ THE PREMISE THAT CHANGES THIS SLICE'S SHAPE — read before anything else

**`renderer/lib/onboard-workspace.ts` deliberately collapses the partial state, and says so in its own header (`:8-10`):**

> *"This wrapper folds a typed err (validation / store fault / auth) OR any transport error OR a malformed ok to `{ ok: false }` so a failed onboarding never surfaces a raw driver cause / **partial state**"*

Its result type is binary:
```ts
export type OnboardResult =
  | { readonly ok: true; readonly workspace: UiSafeProvisioned }
  | { readonly ok: false };              // :29-31
```

⇒ **Worker's new `ONBOARDING_PARTIAL_SCAFFOLD` will arrive and be flattened to `{ok:false}` before any surface sees it.** So this slice is **not** "add a repair UI on top of an existing signal" — it must **widen a deliberately-narrow fold**, and that fold exists for a real reason (redaction-safety: never surface a raw driver cause). **Widening it carelessly re-opens exactly what desktop L6 closed.**

## ⭐ TWO of 9.21's THREE Done-when clauses are ALREADY SATISFIED — verify this, then don't rebuild them

9.21's Done-when: *"a partial scaffold surfaces a typed repair state; re-run resumes idempotently; onboarding never marks complete on a partial."*

1. **"re-run resumes idempotently"** — ✅ **satisfied by leg A's code and pinned there** (`provisionWorkspace.ts` same-type branch unions the registry; `resume_after_partial_completes_the_union` + `resume_does_not_restore_a_revoked_ack`, both mutation-verified). Nothing for you to build.
2. **"onboarding never marks complete on a partial"** — ✅ **ALREADY TRUE, and by accident.** `surfaces/onboarding/index.tsx:91-97` calls `onOnboarded(...)` only on `r.ok`, and `App.tsx:223-240`'s handler is what fires `markOnboarded()`. Since the fold turns a partial into `{ok:false}`, `markOnboarded()` **cannot** fire on a partial today.
   ⛔ **THAT IS THE RISK IN THIS SLICE.** The correctness is **incidental to the blanket fold you are about to widen.** The moment `partial_scaffold` becomes a distinguishable third state, the guarantee stops being structural and becomes something your branching has to preserve deliberately. **Pin it before you widen anything.**
3. **"a partial scaffold surfaces a typed repair state"** — ⬜ **the only genuinely missing clause. This is the slice.**

## ⚠ The current copy is actively wrong for a partial

`surfaces/onboarding/index.tsx:98` renders `"Couldn't create the workspace. Check the vault path and try again."` on every failure. For a partial scaffold:
- *"Couldn't create the workspace"* — **false.** The config row was durably written.
- *"Check the vault path"* — **misdirection.** The vault path was fine; the registry union faulted.
- *"try again"* — **accidentally correct** (re-running genuinely resumes) but for a reason the copy doesn't convey, so the user has no way to know retrying is the right move rather than a guess.

## Things to flag at Step 2.5

1. ⛔ **Shape of the widened `OnboardResult`.** (a) `{ok:false, partial:true}` — minimal, but `ok:false` with an actionable state is a slightly odd read. (b) A three-arm discriminated union on an `outcome` tag — clearest, larger diff. (c) `{ok:false, reason:"partial_scaffold"|"failed"}`. **My default vote: (c)** — one new optional discriminant, every existing `if (r.ok)` caller stays correct by construction, and the redaction surface stays exactly one field wide. Argue (b) if you think the call sites read better; ⛔ **whatever you pick, the acceptance bullet that matters is that only ONE new case is admitted.**
2. **Does `App.tsx` need to change, or can the surface absorb the partial entirely?** The surface already owns its error state. **My default vote: keep it in the surface** — `App.tsx`'s handler exists to record a *completed* onboarding, and a partial is not one. Fewer moving parts and it keeps `markOnboarded` untouched.
3. **Is the resume affordance a distinct button or just the existing submit?** Re-submitting the same input *is* the resume. **My default vote: reuse the existing submit, with copy that says so** — a separate "Resume" button implies a separate mechanism and would need its own path. Say which.
4. **Should the partial state persist across an app restart?** ⛔ **My default vote: NO, out of scope.** The durable truth already lives in the worker's store, and re-running onboarding re-derives the state. Persisting it in the renderer would be a second source of truth. Flag if you think the user needs it across a restart — that's a real product question and I'd route it up rather than guess.
