# /tdd brief — outbox_entry_persists_approval_policy_field

## Feature
Add an additive, nullable `approvalPolicy?: string` field to `OutboxEntry` (both Drizzle
dialects + both adapters) so `24.15`'s redrive fix has somewhere to persist the original
`approvalPolicy` string. Pure schema/plumbing — no design decision, no behavior change to
anything that doesn't reference the new field yet.

## RED test outline (Step 2)
Tests to add in `packages/db/test/contract/repository-contract.test.ts` (runs against both dialects):

1. **`outbox_entry_round_trips_approval_policy`** — Asserts: `enqueue()` an entry with `approvalPolicy: "auto_private"`, `get()` it back, `.approvalPolicy` equals `"auto_private"`. Why: pins the storage half `24.15` depends on — a construction-only field (built but not persisted) is exactly the shape condition-(d)'s L134/`24.7` family has repeatedly flagged as a false green in this round; this test proves the value actually crosses the DB boundary.
2. **`outbox_entry_approval_policy_defaults_undefined_when_omitted`** — Asserts: an entry enqueued without `approvalPolicy` reads back `undefined` (not `null`, not `""`). Why: confirms additive-nullable is real — existing rows / existing callers must not break or silently coerce.
3. **`outbox_entry_update_persists_changed_approval_policy`** — Asserts: `enqueue()` without the field, then `update()` setting `approvalPolicy: "manual"`, then `get()` returns `"manual"`. Why: the `update()` path is the one with an explicit field-by-field `.set({...})` block (not a spread) — the field most likely to be silently missed if the two adapters' blocks are edited by hand and one is forgotten.
4. **`column_parity` (existing test, no new test needed — just confirm it still passes)** — `packages/db/test/schema/column-parity.test.ts:114` already walks the SQLite/Postgres schema pair; adding the column to only one dialect fails this test. Cite it in the Step-9 report as a passing regression guard, don't duplicate it.
