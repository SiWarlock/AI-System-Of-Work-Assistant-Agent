## ⚠ The non-obvious half: the fail-closed default must FLIP
`failClosedEgress` (`boot.ts:533-535`) returns `zeroEgressOnly: true` on an absent/faulted read. That was coherent under the OLD semantics (`!acknowledged` ⇒ "raw egress is off" ⇒ restrictive). Under the CORRECT semantics it inverts: `true` becomes a **positive safety claim** ("content stays local"), so returning `true` when the store read FAILED asserts a safety property we could not verify — a false assurance precisely at fault time, which is the moment it's most likely to be believed. Fixing the happy path and leaving `failClosedEgress` alone would replace one false assurance with another. The fail-closed value for an unverifiable positive safety claim is the NON-claiming one.

## Things to flag at Step 2.5
1. **Empty allowlist ⇒ `true` or `false`?** (a) `false` — "nothing allowed" isn't "pinned to local"; (b) `true` — nothing can egress, so it's trivially zero-egress. My default vote: **(a) `false`**. (b) is defensible in pure logic and wrong in effect: the field is rendered to a human as a local-only assurance, and an empty allowlist is far more likely to mean unprovisioned/misconfigured than deliberately-local. Never let "unconfigured" render as a safety guarantee. Say so if you disagree — this one is a genuine judgement call, not a mechanical one.
2. **Where does the predicate live?** (a) export `LOCAL_PROVIDERS` from `@sow/policy` and test membership in `boot.ts`; (b) export a predicate (`isZeroEgressOnlyAllowlist(processors)`) from `@sow/policy` and call it; (c) inline the check in `boot.ts`. My default vote: **(b)** — it keeps the set module-private (its comment is emphatic that provider identity wins over endpoint claims, i.e. it does not want callers reasoning about membership themselves), puts the ALL-not-ANY logic next to the authority, and gives test 8 something to pin. (c) is forbidden.
3. **Which allowlist is "effective" — `allowedProcessors` or `rawContentAllowedProcessors`?** They're seeded identically today, so the choice is invisible now and won't be later. My default vote: **require BOTH to be local-only** (the claim "content stays local" is false if raw content may go anywhere non-local), and say explicitly in the doc comment which fields the predicate reads.
4. **Wording of the corrected contract.** My default vote: keep the existing "pinned to a local zero-egress provider" phrasing and make the code match it, rather than re-documenting the field to describe the old buggy behavior. The doc was right; the producer was wrong.
5. **Does the fail-closed inversion deserve its own commit?** My default vote: **no — one commit.** The happy-path fix and the fail-closed flip are two halves of one semantic correction; splitting them would leave an intermediate commit that claims local-only on fault while claiming correctness on the happy path, which is a worse state than either end.
