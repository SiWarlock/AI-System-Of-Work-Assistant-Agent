## Things to flag at Step 2.5

1. ⭐ **THE CRUX — how is "no notice" expressed?** (a) required `egressProcessor: string | null`. (b) a discriminated union, e.g. `notice: {kind:"none"} | {kind:"processor", value: string}`. (c) a required named-object parameter carrying (b). **My default vote: (b), delivered via (c).** Reason: **(a) reproduces the defect in a new shape.** `null` is the value a caller reaches for reflexively, so "this answer genuinely needs no notice" and "I didn't think about the notice" collapse into one token again — and 9.24's entire analysis is that **absence has three meanings.** A named `{kind:"none"}` cannot be typed by accident. ⚠ Push back if (c) churns the call sites more than it's worth; I'd rather have (b) with a positional than (a) with a nice signature.
2. **Does the decline need a *reason*?** e.g. `{kind:"none", because:"not-employer-work"}`. **My default vote: NO — not in this slice.** It's attractive and it's scope creep; the compiler-enforced decision is the safety win, and a reason field invites a free-form string on a rule-5 path. Flag if you think the reason is needed to make the decline *reviewable*.
3. **Is a runtime pin needed as well as the compile pin?** **My default vote: the compile pin is primary and sufficient**, because a `@ts-expect-error` is checked by `tsc --noEmit`, which *is* this repo's `lint` gate and therefore cannot silently stop running. Add a runtime assertion only if the chosen shape leaves a way to satisfy the compiler while still producing a notice-free servable answer — **if you find such a way, that's a finding, tell me immediately.**
