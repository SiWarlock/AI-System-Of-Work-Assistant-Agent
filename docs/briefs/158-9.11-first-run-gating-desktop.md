# /tdd brief — desktop_first_run_gating

## Feature
Add an authoritative, durable first-run gate owned by Electron main (`main/first-run.ts`) so the onboarding surface shows ONLY on a genuine first run — not on a transient empty registry (e.g. the worker unreachable at boot) — persisted to app-data and surfaced to the renderer through the narrow preload bridge. The renderer's onboarding mount consults this signal; a confirmed onboarding marks it complete.

## Use case + traceability
- **Task ID:** 9.17 — a dedicated task completing the first-run-gating leg of the onboarding surface
- **Architecture sections it implements:** `ARCHITECTURE.md §11` (workspace-preset onboarding, first-run) · `§5` (Electron security — preload bridge, REQ-S-004) · `REQ-UX-005` / `WS-6`
- **Related context:**
  - Current gate is renderer-ONLY: `App.tsx:167` `if (!hasAnyOnboardedWorkspace(state))` renders `<Onboarding>`. That state is derived from the live-stream-hydrated onboarded/registry store — so if the worker is unreachable at boot (empty `state.onboarded`), an ALREADY-onboarded install spuriously re-shows onboarding. The plan names this: "onboarding-shows-only-on-first-run is NOT enforced (no `main/first-run.ts`)."
  - Main→renderer signal pattern to mirror: `main/session-token.ts` + the `session:getToken` preload channel (main owns; renderer reads via the bridge). App-data persistence pattern: `main/index.ts:100` `app.getPath("userData")` → `join(userData, "sow.db")`.
  - Pure-module + injected-fs + DOM-less-testable patterns: desktop **LESSON 16** (a pure electron-free predicate, `shell`/electron kept OUT so it tests under the node tsconfig), **LESSON 13** (injected fs seam + persist to app-data, never /tmp/in-memory), **LESSON 3** (window-free DI logic in its own module), **LESSON 15** (`Object.create(null)`, empty=unset hygiene), **LESSON 16** inventory forbidden-regex (`/db|sql|fs|file|secret|keychain|connector|exec|shell/i`) — channel names must clear it.
  - **WS-8 / isolation (LESSON 8/9):** this marker gates ONLY the onboarding-surface MOUNT decision — it must NEVER feed the WS-8 scope/isolation predicate (`isWorkspaceScope` stays keyed on the stable `isGlobal` flag, registry-derived). Single-source-of-truth for isolation stays the registry; the marker is a durable UX gate only.

## Acceptance criteria (what "done" means)
- [ ] A pure, electron-free `main/first-run.ts` reads/writes a durable onboarding-complete marker under app-data over an INJECTED fs seam: `readOnboardingComplete(path, deps)` → typed `Result<boolean, …>`; `markOnboardingComplete(path, deps)` writes it idempotently. Never throws (§16); `shell`/`electron`/`app` are NOT imported into the pure module (tests under the DOM-less node tsconfig, LESSON 3/16).
- [ ] First-run determination is authoritative + durable: marker ABSENT ⇒ first run (show onboarding); marker PRESENT ⇒ not first run (never auto-show onboarding again), independent of the live-stream registry hydration.
- [ ] A marker READ fault fails toward the current registry-derived behavior (never LOCKS OUT a real first-run user, never silently drops a real install into re-onboarding) — the fault is inconclusive, so the gate falls back to `!hasAnyOnboardedWorkspace(state)` (no regression).
- [ ] Two new preload channels — `lifecycle:firstRunStatus` (read) + `lifecycle:markOnboarded` (write the marker) — are registered (exactly one `ipcMain.handle` each), added to `preload/inventory.json`, and clear the inventory forbidden-regex + the `/token/i` assertion; the preload-inventory snapshot test passes with the two additions.
- [ ] The renderer onboarding gate consults the first-run signal: onboarding mounts IFF the durable marker says "never onboarded" (with the read-fault fallback above); a CONFIRMED-complete `createWorkspace` (not a partial/failed one) calls `lifecycle:markOnboarded` so future launches skip onboarding. The gate decision lives in a window-free, DI'd module (LESSON 3) that is unit-tested.
- [ ] The marker gates ONLY the onboarding mount — the WS-8 `isWorkspaceScope`/`isGlobal` predicate is untouched (pinned: an onboarded-but-marker-absent, or marker-present-but-empty-registry, state never relaxes isolation — LESSON 9).
- [ ] All unit tests pass (`apps/desktop/test/main/first-run.test.ts` + the renderer gate module test); `/preflight` clean.

## Wiring / entry point (Step 7.5)
- **Main:** `app.whenReady()` → `startWorker`/boot (`main/index.ts`) resolves `userData` and sets the first-run marker path (mirror `setVaultRoots`); `registerIpcHandlers()` (`main/ipc.ts`) binds `lifecycle:firstRunStatus` → `readOnboardingComplete` and `lifecycle:markOnboarded` → `markOnboardingComplete` with the real `node:fs` seam.
- **Renderer:** `App.tsx` onboarding gate (line ~167) consults `window.sow.lifecycle.firstRunStatus()` (via preload) through the DI'd gate module; `onOnboarded` (line 176) additionally calls `window.sow.lifecycle.markOnboarded()` on a confirmed create.

## RED test outline (Step 2)
1. **`marker_absent_is_first_run`** — `readOnboardingComplete` with no marker file → `ok(false)` (first run). Asserts: absent ⇒ first-run. Why: §11 first-run.
2. **`marker_present_is_not_first_run`** — after `markOnboardingComplete`, read → `ok(true)`. Asserts: durable persistence across the read. Why: §11 first-run-only.
3. **`read_fault_is_inconclusive_never_throws`** — an fs-read throw → a typed err (not a throw), which the gate maps to the registry-derived fallback. Asserts: never-throws + fail-toward-no-regression. Why: §16 / LESSON 13/16.
4. **`mark_is_idempotent`** — marking twice is a safe no-op (no duplicate/partial state). Asserts: idempotent write. Why: §11 idempotent onboarding.
5. **`gate_shows_onboarding_only_when_marker_absent`** — gate module: marker=false ⇒ show; marker=true ⇒ don't show (even if `state.onboarded` empty); read-fault ⇒ fall back to `!hasAnyOnboardedWorkspace`. Asserts: the authoritative gate + fallback. Why: §11.
6. **`gate_never_relaxes_ws8_isolation`** — no marker state (present/absent/faulted) changes the `isWorkspaceScope`/`isGlobal` predicate. Asserts: isolation single-source stays the registry. Why: safety rule 4 / LESSON 9.
7. **`lifecycle_channels_clear_the_inventory_regex`** — `lifecycle:firstRunStatus`/`lifecycle:markOnboarded` pass the forbidden-regex + `/token/i` assertion; inventory snapshot matches. Why: §5 preload security pin.

## Things to flag at Step 2.5
1. **Marker representation — (A) a tiny JSON `{ onboardingComplete: true }` file vs (B) a bare sentinel file's existence.** My default vote: **(A) JSON** — extensible (a future `completedAt`/preset), explicit, and a malformed/partial file is distinguishable from absent (LESSON 15 empty=unset hygiene). Keep it a single small file under `userData`.
2. **Read-fault posture.** My default vote: **inconclusive ⇒ fall back to the current registry-derived gate** (never lock out a real first-run user, never force re-onboarding) — the durable marker is an ADDITIVE authoritative signal, not a new hard lock. Confirm this matches the desired UX.
3. **Who writes the marker — (A) the renderer calls `lifecycle:markOnboarded` on a confirmed create vs (B) main derives it by observing the first workspace.** My default vote: **(A)** — the renderer knows when `createWorkspace` returned a CONFIRMED-complete result (so a partial/failed scaffold does NOT mark complete → onboarding/repair re-shows); main just persists. Keeps the durable marker aligned with "onboarding actually finished," which also sets up the idempotent-repair leg.
4. **Bundle the idempotent scaffold repair/resume leg here, or split it?** The repair leg (a partial `createWorkspace` surfaces a typed repair/resume state, re-run resumes without duplicating — the worker side is already idempotent by LESSON 30 / worker L30) depends on what the `createWorkspace` result exposes for a partial state. My default vote: **SPLIT** — land the authoritative first-run GATE first (clean, self-contained, a Phase-9 exit blocker on its own); the repair/resume handling is a fast-follow leg once we confirm the createWorkspace partial-result shape (flag it as a Residual/next task at Step 9). Bundle only if the implementer finds the partial-state handling is a trivial renderer addition sharing this slice's test surface.
