## The shape — and the one place I am ruling rather than leaving open

⭐ **RULED: a PER-CODE COUNT MAP, not a single count and not a code list.**
- **Not a single count**, because the Done-when requires `ws_scope_mismatch` specifically to be distinguishable, and one number destroys exactly the distinction the field exists to create — the merged-number defect `entityRefsRejected`'s own doc comment argues against.
- **Not a list of codes**, because a count preserves *how many* without ever carrying an instance, and repetition is itself signal for a probing campaign.
- ⛔ **Rule 7, non-negotiable: codes only — never an entity name, never a path, never a slug.** `WithheldReason` is a closed enum of literals, which is what makes this shape safe.
- **Hoisted above the `try`, exactly like the two existing counters, for the reason that comment states.**
- ⛔ **A benign run must yield ZERO signals** (contracts L86 / 13.8m) — *the distinction must hold in BOTH directions*, so **the non-vacuity control is an acceptance criterion, not a nicety**: a test proving the channel is empty on a benign run is worthless without a sibling proving it is non-empty when a withhold fires, and vice versa.

**Open for your Step 2.5 (I have a preference, not a ruling):** whether the map is exhaustive-by-construction (every `WithheldReason` key present, zero-valued) or sparse (only fired codes present). **Exhaustive is my preference** — it makes "this code can fire" discoverable from the type and makes a *newly added* `GroundedPathRefusal` member impossible to forget. **But it interacts with (U1) and with the composed union — if exhaustiveness forces re-declaring the member list, it is the wrong trade and sparse wins.** Tell me which, and why, with the code in front of you.
