## Things to flag at Step 2.5
1. **Where should the correspondence pin live — knowledge's suite (consumer side) or
   contracts' suite (declaration side)?** Default vote: **knowledge** — the claim being
   pinned is "the consumer's assumption still matches the declaration," which is a
   property of the consumer, not the declaration; contracts' own tests already pin the
   declared set's shape independently (leg A). Check first whether contracts already
   has a symmetric test before adding one here, to avoid a duplicate pin maintained in
   two places.
2. **Does the pin need to check anything beyond list *membership* (e.g. the 200-cap,
   nesting-rejection) to count as closing the ruling?** Default vote: **no** — the
   named hazard is specifically *list-ness having exactly one source*; the cap and
   nesting behaviors are already independently pinned on each side (leg A's own schema
   tests; this module's existing `pure_never_throws` / `bounded` tests). Conflating
   them into one pin makes a future failure harder to diagnose (which property broke?).
3. **Is this a Convention-candidate lesson?** Default vote: **yes** — "a
   schema-declared per-field property (list-ness, or any future declared trait) needs a
   correspondence pin in the CONSUMER's suite against the SAME declaration it
   consumes, not a locally-re-derived belief" is a reusable shape beyond this one field.
