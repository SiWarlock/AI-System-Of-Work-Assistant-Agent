# /tdd brief — task_table_migration_and_the_missing_detector

## Feature
Task `13.15`'s `task` table has never had a migration generated, in either dialect, despite being ticked DONE. Generate it — **and, the actual point of this slice, install the detector that would have caught it**: the repo-contract suite builds its test databases directly from the Drizzle schema and never calls `applyMigrations()`, so no existing test could ever fail on a schema table with no migration.

## RED test outline (Step 2)
1. **`migrated_database_has_every_schema_table`** — Asserts: a database built **via `applyMigrations()`** contains every table defined in `packages/db/src/schema/`. **RED today** — `task` is missing. Why: this is the detector; it is the slice's actual deliverable.
2. **`task_table_round_trips_through_a_migrated_database`** — Asserts: `TaskRepository`'s basic write/read works against a DB built by the **migration path**, not the schema path. Why: pins that the generated migration is byte-consistent with the schema, not merely present.
3. **`migration_detector_covers_both_dialects`** — Asserts: test 1 executes on **both** SQLite and Postgres. ⚠ **Confirm via `--reporter=json`, not the default reporter** — your predecessor found the default loses lines to terminal overwrite under capture and appeared to show only one dialect running.

## Things to flag at Step 2.5
1. **Where does the detector live — extend `repository-contract.test.ts`, or a new dedicated migration-parity test file?** My default vote: **a new dedicated file.** The contract suite's whole design is direct-from-schema construction (that is *why* it never caught this), so bolting a migration-path test into it mixes two substrates in one file and invites a later refactor to "simplify" the odd one out. **A separate file whose name states it exercises migrations is harder to accidentally neuter.** State your reasoning either way.
2. **How is the "every schema table" set derived?** My default vote: **enumerate the Drizzle schema barrel programmatically** (the same `getTableColumns`/barrel-walk approach `column-parity.test.ts` already uses for its smoke check), **not a hardcoded list** — a hardcoded list is a snapshot that goes stale the next time someone adds a schema file, which is precisely this task's failure mode one level up. ⛔ **If you find yourself writing a literal array of table names, stop and flag it.**
