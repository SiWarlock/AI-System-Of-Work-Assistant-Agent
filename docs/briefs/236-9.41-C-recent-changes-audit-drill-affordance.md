# /tdd brief — recent_changes_audit_drill_affordance

## Feature
Make a Recent Activity row's `changeId` actionable: on a deliberate user action, call leg B's
`query.auditDrill`, and render the resolved `{event, occurredAt}` summary inline on that row —
fail-closed to a non-committal state on any denial, fault, or malformed result.

separate hydrate is needed"*). ⇒ **Leg C is the first place a drill RESULT's content reaches the DOM.**
That is why the rule-7 / UI-safe questions below are real rather than ceremonial: you cannot copy a
precedent for the part that matters most.

## Acceptance criteria (what "done" means)
- [ ] A new `renderer/lib/audit-drill.ts` mirrors `drilldown.ts`: a `createAuditDrill(client)` returning
      `(workspaceId, changeId) => Promise<AuditDrillResult>`, where the result is a closed union
      (`{ok:true, summary}` / `{ok:false}`) folding **typed denial · transport throw · malformed-but-ok
      runtime value** all to `{ok:false}`. Wired into `live.ts` beside `drillDown`.
- [ ] The fetched summary is **re-validated at the renderer** through `UiSafeAuditDrillSummarySchema`
      (`.safeParse`, drop on failure) before it can render. ⛔ **Not optional and not belt-and-braces:**
      desktop L46 already establishes that worker output is candidate data to the renderer too, and this
      is the arc's first content-bearing crossing.
- [ ] `RecentActivity` (`Today.tsx:220-250`) gains a per-row drill affordance and renders the resolved
      `event` + `occurredAt` inline on success. Per-row state is a 3-state union mirroring
      `egress.tsx`'s `PostureCell`, with the same **monotonic per-row sequence guard** so a slow
      resolution for row A can never paint onto a re-rendered/replaced row A.
- [ ] **Fail-closed presentation:** denial, fault, malformed, or schema-reject all render the SAME
      non-committal state. ⛔ **The four must be indistinguishable in the UI** — a distinguishable
      "denied" vs "not found" is a probe oracle against the audit store; leg B deliberately mints
      distinct codes *server-side* for the operator, and those distinctions must NOT reach the DOM.
      ⚠ This is a real constraint that pulls against normal UX instinct; state it in-code.
- [ ] **The affordance is keyboard-operable and announced** — it is an interactive control inside a
      `role="list"`/`role="listitem"` structure, so it needs a real `<button>` (not a click-handled
      `<div>`), an accessible name that distinguishes rows, and the resolved summary associated with its
      row rather than announced as a free-floating live region. Follow the existing a11y discipline in
      this file's neighbours (desktop L22's roving-listbox rules apply to composite widgets — confirm
      whether this row list qualifies or whether a plain per-row button is correct; **Step-2.5 Q3**).
- [ ] ⛔ **NOTHING beyond `{event, occurredAt}` renders, and no `auditRef`/`actor`/`refs`/`payloadHash`/
      `workspaceId` appears in the DOM** — pinned as an **exact key/attribute inventory** on the rendered
      row, not a name-filter. Desktop **L54** is explicit that a filter-and-assert-nothing-matched pin
      is vacuous exactly where it matters; **L62** is explicit that a phrase blocklist is the wrong shape.
      Pin the **inventory**, and prove non-vacuity by a throwaway probe that adds a forbidden field and
      confirms the test goes RED (desktop **L90**: a negative pin never observed to fail is unproven).
- [ ] The existing empty-state (`:225-232`) and the existing non-drill rendering are unchanged when the
      affordance is never activated — no new network call on mount. ⛔ **Do NOT hydrate drill summaries
      eagerly for every row:** it would turn a passive list into N audit reads per render, and the
      arc's whole posture is that a drill is a *deliberate, individually-gated* act.
- [ ] `/preflight` clean — report as **"typecheck + tests clean; no lint coverage exists"**, never
      "lint clean" (Carry-forward 6(0)).

## RED test outline (Step 2)
**Node tier** (`test/renderer/audit-drill.test.ts` — mirror `drilldown.test.ts`):
1. **`resolves_a_permitted_drill_to_its_summary`** — Asserts: an ok result with a valid summary yields
   `{ok:true, summary:{event,occurredAt}}`. Why: the wrapper's happy path.
2. **`folds_denial_transport_throw_and_malformed_ok_all_to_not_ok`** — Asserts: each of the three
   independently yields `{ok:false}`, **and they are indistinguishable to the caller**. Why: the
   `drilldown.ts:24-32` precedent + the no-probe-oracle constraint.
3. **`a_schema_invalid_summary_is_dropped_not_rendered`** — Asserts: an ok result whose payload fails
   `UiSafeAuditDrillSummarySchema` (e.g. an extra key, or an oversized `event`) folds to `{ok:false}`.
   Why: desktop L46 — worker output is candidate data at the renderer too.

**DOM tier** (`test-dom/`):
4. **`activating_a_row_renders_its_resolved_summary`** — Asserts: activating row 1's control renders its
   `event`/`occurredAt`, and **row 2 is unaffected**. Why: per-row state isolation.
5. **`a_failed_drill_renders_the_same_non_committal_state_as_a_denied_one`** — Asserts: fault and denial
   produce **byte-identical** rendered output. Why: the no-probe-oracle constraint; this is the pin that
   makes it real rather than intended.
6. **`a_superseded_resolution_never_paints`** — Asserts: a slow resolution for a row that has since been
   replaced/re-keyed does not render. Why: `egress.tsx`'s `seq` guard, applied here. ⚠ Drive it with a
   deliberately out-of-order promise resolution, not a timing assumption.
7. **`the_drilled_row_exposes_exactly_the_allowed_keys`** — Asserts: an EXACT inventory of the rendered
   row's text + attributes after a successful drill; no `auditRef`/`actor`/`refs`/`payloadHash`/
   `workspaceId` in any form. Why: rule 7 + the arc invariant. ⛔ **Mutation-verify** (add a forbidden
   field, confirm RED, revert) per desktop L90 — an inventory pin that has never failed is unproven.
8. **`no_drill_request_fires_on_mount`** — Asserts: rendering the list issues ZERO calls until an
   affordance is activated. Why: the deliberate-act posture; also guards against an eager-hydrate
   refactor later.
9. **`the_affordance_is_keyboard_operable_and_named`** — Asserts: it is a real button, reachable and
   activatable by keyboard, with an accessible name distinguishing its row. Why: a11y; the existing
   list is `role="list"`/`listitem`.

## Things to flag at Step 2.5
1. **What is the affordance, concretely — an inline expand-in-place, or a click-to-reveal detail line?**
   My default vote: **click-to-reveal an inline detail line on the row itself** (smallest surface, no new
   layout primitive, keeps the row list a list). ⚠ The competing option (a popover/panel) drags in focus
   management, dismissal semantics, and the roving-listbox contract — real cost for a two-field payload.
   **If you think two fields don't justify an affordance at all, say so** — "render nothing, the arc's
   value is the resolver" is a legitimate answer and I would rather hear it now than build a control
   nobody wants.
2. **Is the resolved summary retained after it is fetched, or re-fetched on each activation?** My default
   vote: **retain per-row for the session, keyed like `egress.tsx`'s `cells`**, with the seq guard making
   staleness safe. Re-fetching every time is more "live" but issues an audit read per click. ⚠ Neither is
   obviously right — the audit record is immutable once written, which argues for retain.
3. **Does this row list need the roving-listbox contract (desktop L22) once rows carry a control?** My
   default vote: **no — a plain per-row `<button>`**, because the rows are `role="listitem"` in a
   `role="list"`, not options in a `role="listbox"`, and L22's contract is about single-tab-stop
   composite widgets. ⚠ **I hold this loosely** — if adding a control per row makes it a composite widget
   in practice (N tab stops through a long feed), L22's reasoning may apply after all. **This is the
   question where I am most likely to be wrong**; check it against L22's actual text rather than my summary.
4. **Should a row with no resolvable summary hide its affordance after a failed attempt?** My default
   vote: **no, keep it retryable** — desktop L53's second half: failing closed on the DISPLAY must not
   strand the action; a permanently disabled control after one transient fault is that defect's shape.

## Lessons-logged candidates anticipated
- **Convention candidate** — "A fetched-on-demand per-row detail reuses the `PostureCell` shape:
  a 3-state union + a monotonic per-row seq guard + fail-closed-to-one-indistinguishable-state. The
  seq guard is not optional the moment the list can re-key underneath an in-flight request."
- **Convention candidate** — "Distinct server-side error codes exist for the OPERATOR, not the DOM:
  collapsing denial/not-found/fault into one rendered state is a deliberate anti-probe measure, and the
  collapse belongs at the renderer boundary rather than by weakening the server's taxonomy."
- **Architecture-doc note candidate** — the arc's `auditRef`-never-leaves-the-worker invariant now has a
  rendered consumer; worth one line confirming the boundary held end-to-end.
