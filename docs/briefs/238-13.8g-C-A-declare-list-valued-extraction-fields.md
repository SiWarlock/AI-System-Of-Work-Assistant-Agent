# /tdd brief — declare_list_valued_extraction_fields

## Feature
Give `sow:agent-extraction` **per-field, schema-declared, default-CLOSED** list support: a field the
schema declares as list-valued may carry a bounded `string[]`; every other field stays scalar-only and
is rejected exactly as today. Declared for `attendees` and `decisions`.

## ⚠ THIS IS A SCOPED, DECLARED, DEFAULT-CLOSED **RELAXATION** OF A RULE-2 GATE
**Say it that way; do not soften it.** After this change the gate admits a value shape it previously
rejected. *Narrow*, *declared* and *default-closed* are **qualifiers, not a reclassification.**
⭐ **The wording is load-bearing because it sets your review posture:** "a prohibition made precise"
invites a reviewer who checks the new rule is well-formed. **"A candidate-data gate was narrowly
relaxed"** invites the reviewer who asks *what can now get through that couldn't* — and therefore asks
the question below, which is the most important one in this slice. (Lead ruling 2026-07-31; the
orchestrator's original framing was corrected on exactly this point.)

⛔ **THE SECURITY QUESTION, MANDATORY, ANSWERED BY CONSTRUCTION AND NOT BY INSPECTION:
CAN A CANDIDATE DECLARE ITS OWN LIST-NESS?** It must not be able to. **The schema declares which fields
are lists; the payload never does.** If any path exists where model output influences which fields are
treated as lists, that is a **rule-2 breach and a Finding to the lead** — not a design detail to resolve
in-slice. `security-reviewer` is **MANDATORY** and this is its first focus area.

## ⭐ THE DESIGN, and the one hazard that can silently undo it
**Verified current state** (`packages/contracts/schemas/agent-extraction.schema.json`, generated):
```
"fields": { "type":"object",
            "additionalProperties": <field schema: value = anyOf[string,number,boolean]>,
            "propertyNames": { "pattern": "^(?!(?:__proto__|prototype|constructor)$)" } }
```
`fields` is `z.record(FIELD_NAME, AgentExtractionCandidateFieldSchema)` — an **open** key set (the §9
field catalog is an `arch_gap`), so `z.record`'s value schema emits as `additionalProperties` and its
**key** schema emits as `propertyNames`.

**The target shape gives default-closed semantics for free, in JSON Schema's own precedence rules** —
`properties` wins over `additionalProperties` for a named key:
```
"fields": { "type":"object",
            "properties": { "attendees": <list-OR-scalar>, "decisions": <list-OR-scalar> },
            "additionalProperties": <scalar-only, unchanged>,
            "propertyNames": { ...unchanged... } }
```
⇒ a declared field may be a list; **every undeclared field keeps today's scalar-only rejection**; and
**the declaration is structural — a payload cannot add itself to `properties`**, which is how the
forgery question above is answered *by construction*. In Zod this is
`z.object({ attendees: …optional(), decisions: …optional() }).catchall(<scalar-only>)`.

⛔ **THE HAZARD — and it is a SECURITY regression, not a cosmetic one.** `propertyNames` is emitted from
**`z.record`'s KEY schema**. `.object().catchall()` **has no key-schema slot**, so switching the
container can **silently drop the `propertyNames` prototype-pollution guard from the generated JSON
Schema** — a guard a **prior security review specifically added** to close an ajv↔Zod parity gap
(`agent-extraction.ts:40-47`: *"Emitted as `propertyNames.pattern` so ajv … REJECTS such a key, rather
than relying on Zod silently DROPPING `__proto__`"*). ⇒ **You must verify `propertyNames` survives in
the REGENERATED `agent-extraction.schema.json` by reading the file — never by assuming the Zod type
implies it.** If it does not survive, that is a Step-2.5 escalation, not something to work around.

## Acceptance criteria (what "done" means)
- [ ] `attendees` and `decisions` are declared list-capable; **both**, not one. ⛔ Declaring only
      `attendees` leaves `decisions`' array branch dead under a task marked closed — **a fresh instance
      of the very defect this task exists to close, created by its own fix** (lead-ruled).
- [ ] ⭐ **LIST-NESS HAS EXACTLY ONE SOURCE.** The declaration lives in one place; the gate reads it;
      consumers read it. ⛔ **No consumer hand-assumes list-ness via a local `Array.isArray` against its
      own belief — that divergence IS the bug, and re-creating it per-consumer only relocates it**
      (lead-ruled). Export whatever the single source is, so worker's leg can consume it rather than
      re-declare it.
- [ ] A declared list is **`string[]` ONLY**: every element validated as a string, **length-capped**,
      and **nesting rejected** (no array-of-array, no array-of-object). Objects and functions stay
      forbidden **everywhere** — that is what `meeting-extraction.ts:70`'s comment actually guards, and
      it is unchanged by this slice.
- [ ] A declared field may **still** carry a scalar or the `TBD` sentinel — this is additive. A list is
      newly *permitted*, never *required*. (REQ-F-017: absence is `TBD`, never invented, never `[]`.)
- [ ] **TWO independent mechanisms, both verified:** Zod rejects, **and** the regenerated JSON Schema
      makes ajv reject — checked by driving the real ajv registry, not by reading the Zod type. A
      compile-time claim over runtime-untrusted bytes is the inverse of the house pattern.
- [ ] ⛔ **`propertyNames`'s prototype-pollution guard survives in the regenerated schema**, verified by
      reading the generated JSON — plus an ajv test that `__proto__`/`prototype`/`constructor` are still
      rejected as field names, **including on a declared list field**.
- [ ] The ADR-008 set moves together: model `.ts` + regenerated `schemas/agent-extraction.schema.json` +
      the schema-snapshot test. ⚠ **PRECISE EXPECTATION: `__snapshots__/agent-extraction.snap` should
      NOT change** — it freezes the *top-level* field-name set, which stays `["fields"]` (L23: a nested
      change ripples through the generated schema, not the top-level `.snap`). **If the `.snap` changes,
      something unintended happened — stop and say so.**
- [ ] ⭐ **Establish whether a cheap test can pin the CORRESPONDENCE — declared-as-list ⟺ consumed-as-list.**
      That is what prevents instance #3, and it is the make-it-unrepresentable pattern aimed at the
      disagreement itself rather than at either half. ⛔ **If no cheap pin exists, say so explicitly in
      the Step-9 flags** — *"we couldn't"* is a fine answer; an unmentioned gap is not (lead-ruled).
- [ ] The criterion is stated **in-code**, so the next list-shaped field is not a judgement call.
- [ ] `/preflight` clean — report as **"typecheck + tests clean; no lint coverage exists."**

## RED test outline (Step 2)
1. **`a_declared_list_field_accepts_a_string_array`** — `attendees` and `decisions` each accept `["a","b"]`.
2. **`an_undeclared_field_still_rejects_an_array`** — the default-closed leg. ⭐ **The most important
   test in the slice** — it is what makes this a scoped relaxation rather than a global one.
3. **`a_declared_list_field_still_accepts_a_scalar_and_TBD`** — additive, not a shape swap (REQ-F-017).
4. **`a_list_element_that_is_not_a_string_is_rejected`** — numbers, booleans, null, nested arrays,
   objects. Drive each **individually**, not batched — individual injection is what makes it
   discriminating (9.41 leg A's precedent).
5. **`a_list_over_the_cap_is_rejected`** — the bound is real, not documentary.
6. **`ajv_rejects_everything_zod_rejects_for_these_cases`** — the two-mechanism requirement, driven
   through the **real registry**. Why: `.refine`-based approaches pass Zod and vanish from JSON Schema
   (LESSONS §3) — this test is what catches that class.
7. **`propertyNames_still_rejects_prototype_pollution_keys_including_on_a_declared_list_field`** — the
   security regression pin for the hazard above. ⛔ Assert against the **generated JSON Schema's actual
   content** as well as behaviour.
8. **`the_top_level_snapshot_is_unchanged`** — pins the L23 expectation; a changed `.snap` means the
   container shape moved in a way nobody intended.

## Things to flag at Step 2.5
1. **How is the single source of list-ness expressed?** Default vote: an exported `const` set of
   declared list field names, consumed by the schema construction — so worker's leg B imports the same
   constant rather than re-listing the names. ⚠ **Whatever you choose, the test is: can a second
   consumer disagree with the first?** If yes, it is not a single source.
2. **`z.object().catchall()` vs keeping `z.record` plus a refinement.** Default vote: **`.object().catchall()`**,
   because a `.refine`/`.superRefine` **does not survive into the generated JSON Schema** (LESSONS §3),
   which would leave ajv unenforcing and silently violate the two-mechanism requirement. ⛔ But confirm
   the `propertyNames` hazard above before committing to it — if `propertyNames` cannot be preserved
   under `.catchall()`, **escalate rather than choosing between the two guards.**
3. **The element cap value.** Default vote: reuse an existing cap if one governs the same threat
   (attendee-list cardinality) rather than minting a number. ⚠ **Per worker L88, only share a constant
   if the two uses would change for the SAME reason** — if this bounds "hostile model output" and the
   other bounds "real-world list size," they are different threat models and want separate constants
   that happen to be equal.
4. **Does `@sow/domain`'s `ExtractionField` need to widen too?** Default vote: check, and if the
   documented structural-compatibility claim becomes false, say so — this may add a second file or a
   comment amendment, and either is fine as long as no doc is left asserting something untrue.

## Lessons-logged candidates anticipated
- **Convention candidate** — "Per-field capability in an open-key-set record: `properties` for the
  declared keys + `additionalProperties` for the rest gives default-closed semantics from JSON Schema's
  own precedence rules, and makes the declaration unforgeable by construction — the payload cannot add
  itself to `properties`."
- **Convention candidate** — "Changing a Zod container shape can silently drop a JSON-Schema-only guard
  (`propertyNames`) that has no Zod-type equivalent; regenerate and READ the artifact."
