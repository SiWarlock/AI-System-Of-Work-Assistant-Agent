## ⛔ THE SHARPEST POINT: the fail-closed DIRECTION INVERTS. Verify this yourself before coding.
Under the old meaning (`!acknowledged`), a fault returning `true` was **fail-SAFE** — "we didn't confirm an ack, so assume the restrictive posture." That is why `boot.ts:532` calls it "safe default" and means it.

Under the new meaning, **`true` asserts *provably* local-only — and a store fault cannot establish that.** So a fault returning `true` becomes a **false assurance on the surface the owner checks to confirm a revoke landed**: the exact defect class this arc exists to delete, reintroduced by the function whose name says it prevents it.

⇒ **My reading: `failClosedEgress` must return `zeroEgressOnly: false`, and its comment must change with it.** `employerRawEgressAcknowledged: false` stays correct and stays fail-safe — only the `zeroEgressOnly` leg inverts. Same for site 3: a post-revoke status must be **derived from the post-revoke workspace state**, not asserted.

This is a premise, not an instruction. If the code says otherwise, that is a Finding — say so at Step 2.5.
