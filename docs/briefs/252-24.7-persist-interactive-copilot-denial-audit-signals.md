# /tdd brief — persist_interactive_copilot_denial_audit_signals

## Feature
Every interactive-Copilot policy denial (the §5 egress veto, the ING-7 admission gate) already builds a redaction-safe `AuditSignal` — and every caller discards it, threading only the human-readable `reason` into the error. This slice wires the ALREADY-BUILT `toAuditRecordInput` → `AuditRepository.append` path (both exist, both are already wired at boot, zero code needed there) into the two live Copilot denial choke points, so a policy boundary being probed becomes a durable, queryable fact instead of an invisible one. **This is arming-block release condition (d) — currently the ONLY thing between here and go-live.**

## Things to flag at Step 2.5
1. **Port shape: a narrow injected `AuditPersistPort` (matching this codebase's existing narrow-port idiom — `CopilotRetrievalPort`, `WorkspacePostureResolver`, `EgressRouteSelector` are all narrow ports in this exact deps chain) vs. injecting `AuditRepository` directly (skips defining a new type, but pulls a `@sow/db` type into `apps/worker/src/api/procedures/*`, which today only import from `@sow/contracts`/`@sow/policy`/`@sow/providers`).** My default vote: **narrow port** — matches the existing pattern in this exact file/deps-chain, keeps the procedures layer's import surface consistent with its neighbors even though `apps/worker` elsewhere does import `@sow/db` directly (e.g. `readModel.ts`, `egressRevoke.ts` — so it's not a hard layering rule, just a local-consistency preference). Disagree if you think matching those other call sites' precedent is stronger than matching this file's own neighbors.
2. **Should the new persist call be fire-and-forget or awaited before returning the `err` to the caller?** My default vote: **awaited** — if persistence silently fails, the caller (and this task's whole done-when) should know, rather than returning a denial that LOOKS durable-audited but wasn't. If awaiting materially changes response latency on the hot path, flag it and we reconsider, but don't default to fire-and-forget for a safety-observability guarantee.
3. **Should a persistence failure (the `AuditRepository.append` call itself erroring) change what the CALLER sees, or only get logged/surfaced separately?** My default vote: **the denial `err` still returns as today (the guarantee — the action stays blocked — must never depend on the audit write succeeding), but the persistence failure itself should be visible somewhere** (a `HealthItem` or equivalent) rather than silently swallowed — name the mechanism you use at Step 9 rather than inventing a new one if an existing "durable-write-that-can-fail" pattern already exists elsewhere in `apps/worker` (check `KnowledgeWriter`/`egressRevoke.ts`'s own failure-handling convention first).
