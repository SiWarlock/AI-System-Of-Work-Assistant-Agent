## Things to flag at Step 2.5

1. **Which package's suite owns the test?** (a) `packages/contracts/test/` — but then contracts' suite asserts things about domain. (b) `packages/domain/test/` — domain already depends on contracts, so it can see both. (c) Split: each package pins itself. **My default vote: (c)** — each package pins its own boundary, so the test lives where the violation would occur and neither suite reaches across a seam to police another. Costs one small duplicated helper; argue (b) if you'd rather have one place.
2. **How do you enumerate imports — regex over source, `ast-grep`, or the TS compiler API?** **My default vote: a regex/text scan over `git ls-files`-enumerated sources**, matching the house pattern from 9.29's writer census (`git ls-files`-anchored so build artefacts can't produce a false red). ⚠ **State the blind spot you accept** — a text scan misses dynamic `import()` with a computed specifier. That's fine if named; it's the L26 "documented candidate" posture.
3. **Do `devDependencies` count?** `typescript`/`vitest` are obviously fine. But a `devDependency` on `@sow/db` would let a *test* import downstream while `src` stayed clean. **My default vote: assert on `dependencies` strictly, and on `devDependencies` allow only a named toolchain set** — so a new internal devDep trips it. Flag if you think that's over-tight.
4. **Does the invariant hold for `test/` as well as `src/`?** The forbidden pattern says the *packages* are pure. A test importing downstream would be a layering smell but not a runtime violation. **My default vote: scan `src/` strictly; report what `test/` looks like without asserting on it this slice** — and if `test/` turns out to already import something downstream, that is a **finding to report**, not a scope expansion.
