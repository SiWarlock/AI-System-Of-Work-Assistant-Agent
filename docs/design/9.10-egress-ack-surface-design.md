## Why this needs review before build
9.10 is not just a settings screen. Today the Employer-Work egress veto is **fail-closed by construction**: `egressVeto()` (`packages/policy/src/egress.ts:74`) reads `egress.employerRawEgressAcknowledged` (boolean), and **there is no durable store for that flag** — it is derived per-request as a `WorkspacePosture` and defaults to `false` **everywhere** (`copilot.ts:315`, `boot.ts:524/:1141`, `presetProfiles.ts:59`). There is **no `EgressPolicyRepository`**. So raw Employer-Work content can never egress to a cloud processor today — it structurally fails closed (`DENY EMPLOYER_RAW_EGRESS_UNACKNOWLEDGED`, no cloud fallback).

REQ-S-002 (§5/§11) requires the owner to be able to **see** egress status and **acknowledge** the Employer-Work raw-egress gate. Implementing the "acknowledge" action therefore means **building the very mechanism that can relax rule #5** — the durable per-workspace ack the veto reads. That is a safety-load-bearing control, so its design (default posture, confirmation UX, un-ack path, audit) is the owner's call, not an agent default.

**Nothing about building this arms anything by itself:** the default stays `false` (fail-closed). The "arming" is literally the owner deliberately acknowledging in the UI. But we must agree the control's shape before it exists.

## What exists (map, not design)
- **Veto enforcement:** `egressVeto(job, route, egress, workspace)` — pure, fail-closed, never throws. When `workspace.type==='employer_work' && job.carriesRawContent===true && employerRawEgressAcknowledged===false` → only a loopback-local route survives; any egress processor → `DENY EMPLOYER_RAW_EGRESS_UNACKNOWLEDGED`, **no cloud fallback** (`egress.ts:119-134`).
- **Contract:** `EgressPolicy { workspaceId, allowedProcessors[], rawContentAllowedProcessors[], employerRawEgressAcknowledged, acknowledgedAt? }` (ARCHITECTURE §Appendix-A; model in `packages/contracts`).
- **Health signal:** every egress decision (allow AND deny) emits `EGRESS_STATUS_HEALTH_CLASS = "egress_status"` (`egress.ts:46`) — currently a policy-internal field **dropped at the AuditRecord boundary** (`.strict()` schema).
- **System Health surface:** built (14.3, `apps/desktop/renderer/surfaces/system-health/index.tsx`) renders `UiSafeHealthItem`; `toUiSafeHealthItem` drops `auditRef`/subjectRef.
- **Commands surface:** `apps/worker/src/api/procedures/commands.ts` currently has ONLY `decideApproval` + `disposeTriage` — no egress command. The renderer never flips policy locally.

## What 9.10 would add (four legs)
1. **NEW durable per-workspace ack store** the veto reads (the load-bearing piece — an `EgressPolicyRepository` or an `EgressAck` field on `WorkspaceConfig`). Cross-track: contracts + db + worker.
2. **NEW worker mutation** — an egress-ack / un-ack command in `commands.ts` (`.mutation()`), authed, audit-logged. Renderer invokes it; never flips locally.
3. **NEW renderer surface** — `apps/desktop/renderer/surfaces/workspace-settings/egress.tsx` (absent): shows per-workspace egress status (acknowledged vs fail-closed) + the acknowledge/revoke action + the allow/deny egress stream from System Health.
4. **Audit-link** — surface `auditRef` as an **opaque worker-mediated ref** (never raw), mirroring 9.5's opaque `changeId`. **Shares design with 9.5's Recent-Changes audit-link** → co-design, ship as its own reviewed slice.

## Owner decisions requested (load-bearing)

**D1 — Approve an in-app control that can relax the Employer-Work raw-egress veto at all?**
- **A (recommended):** Yes — build the durable ack store + explicit acknowledge action, default `false` (fail-closed), owner-only, audit-logged. This is REQ-S-002's intent. The veto stays fail-closed until the owner deliberately acknowledges per workspace.
- **B:** Visibility-only for now — build the **status surface** (read-only: "Employer-Work raw egress is BLOCKED/fail-closed") + the egress allow/deny stream in System Health, but **defer the acknowledge command** to a later owner-gated slice. Nothing can relax the veto yet.
- **C:** Defer 9.10 entirely past Phase-9 exit (treat as a Residual; /phase-exit 9 waives it with a note).

**D2 — If D1=A: acknowledgment scope + durability.**
- Per-workspace (recommended; matches the `EgressPolicy.workspaceId` contract) vs global.
- Durable-until-revoked (recommended) vs session-scoped vs time-expiring (`acknowledgedAt` + a TTL that auto-reverts to fail-closed).

**D3 — If D1=A: confirmation UX (anti-fat-finger for a safety flip).**
- **Recommended:** a deliberate two-step confirm (e.g. a typed workspace name or an explicit "I understand raw Employer-Work content may leave this device" modal), audit-logged with `acknowledgedAt` + actor. A single toggle is too easy to flip by accident for a rule-5 control.

**D4 — Invariants I will pin in the brief regardless of D1–D3 (confirm these hold):**
- Default posture stays `false`/fail-closed everywhere; the store's ABSENCE = fail-closed (no default-true path).
- The renderer NEVER mutates policy locally — only via the authed worker command; the worker owns durable state.
- Even acknowledged, egress still respects `allowedProcessors`/`rawContentAllowedProcessors`; **OpenRouter is its own processor, never an OpenAI alias** (rule #5); the local zero-egress path remains the fail-closed fallback.
- The acknowledge command is audit-logged (actor + `acknowledgedAt` + workspace); a revoke path exists and is equally audited.
- No raw content/secret ever reaches the renderer — status + opaque refs only (rule #7 / forbidden-pattern #5).
